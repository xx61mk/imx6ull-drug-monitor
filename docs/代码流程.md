# 代码流程

从板子上电到屏幕出现曲线，这套代码一共走五段路：**启动链 → 应用初始化 → 线程与邮箱 → 数据流 → UI/云端消费**。下面按这个顺序拆，每一段都对应到具体文件和函数。

---

## 一、启动链：谁把程序拉起来的

```
上电
 └ BootROM
    └ U-Boot（SPL + u-boot.img，fatload/ext4load 到 DDR）
       └ Linux 内核（zImage + imx6ull-xxx.dtb，设备树在这里被解析）
          └ 挂载 rootfs（ext4 或 nfs）
             └ /etc/init.d/rcS → 启动脚本
                └ ./demo        ← 本项目从这里开始
```

应用启动前，内核和启动脚本必须先备好三样东西，否则程序一起来就报错：

| 前置条件 | 谁准备 | 应用里对应的代码 |
|---|---|---|
| `/dev/fb0` 存在 | 内核 fb 驱动 + 设备树 `display` 节点 | `fbdev_init()` |
| `/dev/input/eventX` 存在 | 内核 input 子系统 + 触摸屏驱动 | `evdev_init()` |
| `/dev/i2c-1`、`/sys/bus/w1/devices/` | 内核 I2C / 1-Wire 驱动 | 采集线程读传感器 |

设备树里要开的是这几类节点：LCD 时序（`display-timings`）、触摸控制器（I2C 从设备 + `interrupt`）、DS18B20 所在引脚（`gpio` 或 `w1-gpio`）、门磁与泄漏检测（`gpio-keys`）、继电器与蜂鸣器（`gpio-leds` 或自定义 `gpio`）。

## 二、应用初始化：`main()` 的十五行主线

入口在 `main.c:101`。顺序不能乱，每一步都依赖上一步的结果。

```c
lv_init();                    // ① LVGL 内核：内存池、定时器、对象系统
fbdev_init();                 // ② 打开 /dev/fb0，mmap 出显存，拿到分辨率

static lv_color_t buf1[800*480], buf2[800*480];
lv_disp_draw_buf_init(&disp_buf, buf1, buf2, 800*480);   // ③ 双缓冲
disp_drv.flush_cb = fbdev_flush;                          //    刷屏回调
disp_drv.full_refresh = 1;
lv_disp_drv_register(&disp_drv);

evdev_init();                 // ④ 打开 /dev/input/eventX
indev_drv.read_cb = evdev_read;
lv_indev_drv_register(&indev_drv);                        // ⑤ 触摸输入
lv_indev_set_cursor(mouse_indev, cursor_obj);             //    光标图标

Link_t *pmail = create_mailbox_system();                  // ⑥ 建邮箱（空链表）
mqtt_init();                                              // ⑦ 连云（可选）
register_thread_mailbox(pmail, "get_data",  get_data_th); // ⑧ 注册即启动线程
register_thread_mailbox(pmail, "show_data", show_data_th);
register_thread_mailbox(pmail, "save_data", save_data_th);

ui_init();                    // ⑨ SquareLine 生成的界面，建控件树

while (1) {                   // ⑩ 主循环：只做两件事
    lv_timer_handler();
    if (g_data_seq != last_seq) { ... ui_update_data(...); }
    usleep(5000);
}
```

两个容易踩的点：

- **⑥⑦⑧ 的顺序有讲究**：邮箱必须先建，`mqtt_init()` 要在数据线程启动前完成。否则 `get_data` 线程 3 秒后就来数据，而 MQTT 还没连上，第一批数据白白丢掉。
- **⑨ 放在 ⑧ 之后**：线程先跑起来不会出问题，因为 `show_data_th` 只写共享结构体、不碰控件；界面控件由 `ui_init()` 建好之后主循环才开始刷新。

## 三、邮箱：这套代码的核心

`mailbox.c` 干的事一句话概括：**用一条链表当"线程注册表"，每个节点挂一个队列，按线程名投递、按线程 ID 取件。**

### 数据结构关系

```
Link_t (链表)
 └ Node_t ─┬─ data.name   "get_data" / "show_data" / "save_data"   线程名
           ├─ data.tid    pthread_create 拿到的线程号
           ├─ data.pfun   线程入口函数
           ├─ data.pque   LQue_t*  ← 这个线程专属的链式队列
           ├─ data.mutex  保护队列的互斥锁
           ├─ data.sem    信号量，队列空则阻塞
           └─ pnext
```

定义在 `link.h:11`（线程任务节点）和 `linkqueue.h:33`（队列）。

### 注册：`register_thread_mailbox()`（`mailbox.c:21`）

```c
pinsert->data.pque = create_link_queue();   // 建空队列
pthread_mutex_init(&pinsert->data.mutex);   // 建锁
sem_init(&pinsert->data.sem, 0, 0);         // 信号量初值 0
pthread_create(&pinsert->data.tid, ..., pinsert->data.pfun, NULL);  // 线程立刻开跑
```

注意 `pthread_create` 在这里就调了——**注册即启动**，没有单独的 start 步骤。新节点用头插法放进链表（`mailbox.c:45`），所以链表顺序和注册顺序是反的，这不影响功能，因为投递靠名字查找、取件靠 tid 查找。

### 发送：`send_mail_msg(send_name, data, recv_name)`（`mailbox.c:69`）

```c
遍历链表，strcmp(node->name, recv_name) 找到目标节点
    ↓
qdata.data = mydata;  strcpy(发送者名);  strcpy(接收者名);
    ↓
pthread_mutex_lock(&node->mutex);
push_link_queue(node->pque, qdata);   // 入队（链式队列，malloc 新节点）
sem_post(&node->sem);                 // 唤醒消费者
pthread_mutex_unlock(&node->mutex);
```

一条数据要投给几个线程，就调几次 `send_mail_msg`。`get_data_th` 里就是连调两次（UI 一份、存储一份），纯逻辑版 `project/src/main.c:27` 调了三次（多一个 `send_data`）。

### 接收：`recv_mail_msg(&data, sender)`（`mailbox.c:99`）

```c
mytid = pthread_self();               // 我是谁
遍历链表，找到 tid == mytid 的节点    // 每个线程只知道自己的队列
    ↓
sem_wait(&node->sem);                 // 队列空就睡着，不占 CPU
pthread_mutex_lock(&node->mutex);
pop_link_queue(node->pque, &qdata);   // 出队
pthread_mutex_unlock(&node->mutex);
```

**设计好处**：生产者和消费者互不认识，只认识"名字"和"自己的队列"。加一个消费者（比如报警线程）不需要改采集线程任何一行，注册一下、多发一次就行。

**一个隐患**：`pop_link_queue` 返回 -1 时（理论上不会，因为 sem 和队列同步），`recv_mail_msg` 直接返回 -1，消费者 `continue` 空转，会烧 CPU。实际因为 sem 与 push 严格配对，触发不到。

## 四、一次采集的完整数据流

以 UI 版为例，假设现在是第 N 次采样：

```
get_data_th (main.c:28)                         每 3 秒一次
  │ 组包 struct msgdata：id / cnt / temp / hum / tim
  ├─ send_mail_msg("get_data", data, "show_data") ──┐
  └─ send_mail_msg("get_data", data, "save_data") ──┼──┐
                                                    │  │
        ┌───────────────────────────────────────────┘  │
        ▼                                              ▼
show_data_th (main.c:56)                        save_data_th (main.c:77)
  recv_mail_msg → 阻塞直到 sem_post              recv_mail_msg
  pthread_mutex_lock(&g_data_mutex)              printf 落日志
  g_latest = data                                 #ifdef WITH_MQTT
  g_data_seq++                                     mqtt_send("temp", ...)
  pthread_mutex_unlock                             mqtt_send("hum",  ...)
        │                                        #endif
        │ （不碰任何 LVGL 对象）
        ▼
主循环 (main.c:157)
  if (g_data_seq != last_seq):
      lock → d = g_latest → unlock
      ui_update_data(d.temp, d.hum, d.id)   (UI/ui_data.c:6)
          lv_label_set_text_fmt(ui_ValueTemp, "%.1f", temp)
          lv_label_set_text_fmt(ui_ValueHum,  "%.1f", hum)
          lv_chart_set_next_value(ui_Chart, ui_ChartTempSer, ...)
  lv_timer_handler()   ← 真正把控件画到 framebuffer
```

**为什么要绕这一圈 `g_latest + g_data_seq`？**

LVGL 8 不是线程安全的。如果在 `show_data_th` 里直接 `lv_label_set_text()`，主线程正好在 `lv_timer_handler()` 里遍历同一个控件树，轻则画面错乱，重则野指针崩溃——而且这种崩溃往往跑几十分钟才出现，极难复现。

现在改成：工作线程只写一个普通结构体（加锁保护），主线程看到序号变了才去改控件。**所有 LVGL 调用都发生在主线程**，从根上避开了竞争。代价是最多 5 ms 的显示延迟（`usleep(5000)`），肉眼无感。

## 五、UI 层：SquareLine 生成的代码怎么接进来

`UI/` 是 SquareLine Studio 导出的，不要手改——下次重新导出会被覆盖。要加自己的逻辑，另开文件：

| 文件 | 谁生成 | 能否改 |
|---|---|---|
| `UI/ui.c` `UI/screens/*.c` `UI/fonts/*` | SquareLine 导出 | 不改，重导出会覆盖 |
| `UI/ui_data.c` | 手写 | 可以，数据刷新接口都放这 |
| `UI/components/ui_comp_hook.c` | SquareLine | 留空 |

`ui_update_data()` 里的空指针判断是必须的：

```c
if (ui_ValueTemp) lv_label_set_text_fmt(ui_ValueTemp, "%.1f", temp);
```

界面还没建完、或者某个屏被删掉时，控件指针是 NULL，不判会直接段错误。

## 六、云端链路：`mqtt.c`

### 初始化（`mqtt.c:49`）

```c
pack_topic(DEV_NAME, PRODUCT_ID);          // 拼 OneNET 物模型 topic
    topic[0] = "$sys/{产品ID}/{设备名}/thing/property/post/reply"   订阅
    topic[1] = "$sys/{产品ID}/{设备名}/thing/property/post"         发布

MQTTClient_create(&client, NEW_ADDRESS, CLIENTID, MQTTCLIENT_PERSISTENCE_NONE, NULL);
MQTTClient_setCallbacks(client, NULL, connlost, msgarrvd, delivered);   // 掉线/收消息/送达
conn_opts.keepAliveInterval = 20;
conn_opts.username = PRODUCT_ID;           // OneNET 鉴权：用户名是产品 ID
conn_opts.password = PASSWD;               // 密码是带签名的 token
MQTTClient_connect(client, &conn_opts);
client_ready = 1;
```

**关键设计：连不上不退出。** `mqtt_init()` 失败只返回错误码，`client_ready` 保持 0。`mqtt_send()` 进来先看这个标志，没连上就打印一行跳过。这样没网的情况下屏幕照常显示、本地照常记录，只是不上云——否则在运输途中一断网，整个终端就停了。

### 发布（`mqtt.c:90`）

```c
sprintf(message, "{\"id\":\"%d\",\"version\":\"1.0\",\"params\":{\"%s\":{\"value\":%f}}}",
        id++, key, value);
```

这是 OneNET 物模型要求的上报格式，`key` 必须和云平台上物模型的标识符一模一样（`temp`、`hum`），否则平台收到但不入库。

发完 `MQTTClient_waitForCompletion(client, token, 10000)` 等确认，然后 `sleep(1)`。这个 1 秒的 sleep 是同步阻塞的——意味着 `save_data_th` 每秒最多发一条。**要发多条属性时这句就该去掉**，改成批量组一个 JSON 一起发，否则三条属性要 3 秒。

### 三个回调

| 回调 | 触发时机 | 现在做的事 |
|---|---|---|
| `delivered` | QoS1 消息被 broker 确认 | 记录 token |
| `msgarrvd` | 收到订阅的消息 | 打印 payload |
| `connlost` | 连接断开 | 打印原因 |

`connlost` 里目前只打印。真要断线重连，得在这里起一个重连线程（`MQTTClient_connect` 不能在回调里直接调，会死锁）。

## 七、编译：Makefile 把什么编进去了

顶层 `Makefile`（带 UI）：

```bash
make                              # 本机 x86 调试，产物 ./demo
make CC=arm-linux-gnueabihf-gcc   # 交叉编译到板子
make WITH_MQTT=1 CC=arm-linux-gnueabihf-gcc
```

`WITH_MQTT=1` 做两件事（`Makefile:49`）：

```makefile
CFLAGS += -DWITH_MQTT                              # 打开 main.c 里的 #ifdef
CFLAGS += -I$(LVGL_DIR)/project/include/src        # paho 头文件
LDFLAGS += -L... -lpaho-mqtt3c -lssl -lcrypto
```

不加这个宏，`main.c` 里所有 MQTT 相关代码被预处理掉，编出来的程序不依赖网络库——方便先在板子上把界面和线程调通，再上云。

`CSRCS += project/src/mysqlite.c` 且 `LDFLAGS += -lsqlite3` 也写了，说明构建系统一开始就为存储留了位置。

纯逻辑版 `project/src/Makefile` 更简单，直接一个 `app` 可执行：

```bash
arm-linux-gnueabihf-gcc main.c linkqueue.c link.c mailbox.c mysqlite.c mqtt.c \
  -o app -lpthread -lsqlite3 -lpaho-mqtt3c -lrt -lssl -lcrypto
```

不用板子、不用屏幕，跑在 PC 上就能验证邮箱和线程逻辑对不对——建议每次改完邮箱机制先跑这个。

| **SQLite 存储** | WAL、滚动清理、断电保护 | ⚠️ **`mysqlite.c` 只有一行 include**，存储目前是 `printf` |

也就是说：**框架层（线程、解耦、显示、上云）是真代码，业务层（真实采集、存储、控温、报警）还没接上。** 这不算丢人——先把架构跑通再填业务是正常顺序，讲的时候按这个顺序讲就行。

## 九、补齐业务的接入点

如果要把上面 ⚠️/❌ 的部分接上，改这几个地方就够，不用动架构：

### 1. 真实采集：只换 `get_data_th` 的取数部分

```c
/* DS18B20：内核 1-Wire 驱动读出的是文本 */
int fd = open("/sys/bus/w1/devices/28-xxxxxxxx/w1_slave", O_RDONLY);
/* 末尾 "t=25312" 表示 25.312℃，除以 1000 */

/* LM75：读 /dev/i2c-1，地址 0x48 */
int fd = open("/dev/i2c-1", O_RDWR);
ioctl(fd, I2C_SLAVE, 0x48);
read(fd, buf, 2);          /* 高字节 + 低字节，右移 5 位得 0.125℃ 精度 */

/* ADXL345：SPI 设备，读 /dev/spidev2.0 的三轴加速度 */
/* 幅值偏离 1g 超过阈值 → 判定碰撞/倾倒 */
```

`struct msgdata` 里已经留了 `v`（振动）和 `a`（加速度）两个字段（`linkqueue.h:14`），接 ADXL345 时直接填，投递链路不用改。

### 2. SQLite：`mysqlite.c` 里补四个函数

```c
int  db_init(const char *path);                        // open + 建表 + WAL
int  db_insert(const struct msgdata *d);               // 一条记录落盘
int  db_query_recent(struct msgdata *out, int n);      // 查最近 N 条
void db_cleanup(int keep_days);                        // 删过期数据
```

`db_init` 里三条 PRAGMA 是关键：

```sql
PRAGMA journal_mode = WAL;      -- 读写不互斥，掉电不易损坏
PRAGMA synchronous = NORMAL;    -- 兼顾安全与写入速度
PRAGMA auto_vacuum = INCREMENTAL;
```

然后在 `save_data_th` 里把 `printf` 换成 `db_insert(&mydata)`，`db_cleanup` 挂在每天一次的定时逻辑里。**写入必须在存储线程内做**，SQLite 的句柄不要跨线程共享。

### 3. 控温与报警：新增一个线程，注册进邮箱

```c
register_thread_mailbox(pmail, "ctrl_data", ctrl_data_th);
/* get_data_th 里加一行 send_mail_msg("get_data", mydata, "ctrl_data"); */
```

`ctrl_data_th` 里做两件事：判温度区间写继电器 GPIO（`/sys/class/gpio/gpioN/value`），判四类异常触发蜂鸣器。**控温要加回差**，否则在 8℃ 边界上继电器会来回跳。

这样加线程不用改任何已有代码——只需注册 + 多发一份，这正是邮箱机制的价值。

## 十、跑起来怎么验证每一步

按这个顺序自检，出问题能立刻定位到层：

| 步骤 | 命令 | 期望 |
|---|---|---|
| 1. 屏幕通 | `cat /dev/urandom > /dev/fb0` | 屏幕出现雪花 |
| 2. 触摸通 | `evtest` | 点屏幕有坐标输出 |
| 3. UI 起得来 | `./demo` | 出现界面，光标能拖动 |
| 4. 线程在跑 | `ps -T -p $(pidof demo)` | 看到 4 个线程 |
| 5. 邮箱通 | 看 stdout | 每 3 秒一行 `get_data->save` |
| 6. 界面刷新 | 看屏幕 | 数值 3 秒变一次，曲线在加 |
| 7. 传感器通 | `cat /sys/bus/w1/devices/28-*/w1_slave` | 出现 `t=25xxx` |
| 8. 云通 | OneNET 控制台设备状态 | 显示在线，属性有数据 |
| 9. 断网 | `ifconfig eth0 down` | 程序不退出，屏幕继续刷新 |
